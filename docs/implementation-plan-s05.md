# S05 · Управление своими видео

**Статус · Частичная реализация; корректировка документации для согласования.** S03 уже в `main` (merge `f120ac2`). Базовое переименование в API и кабинете реализовано на основе S03, проверено и предварительно принято независимым review по представленным доказательствам. Сквозная проверка переименования, повтор обработки, удаление при живом FFmpeg и отзыв HLS требуют фактического кода S04. Весь T501, AC-005 и S05 остаются незавершёнными. Согласована публикация проверенной части T501.1 и документации через PR; merge требует отдельного разрешения.

Основание: [T501–T503](../tasks.md#s05--управление-своими-видео), [FR-008, FR-010 и AC-005–006](product-spec.md), [контракты надёжности](homework-05/reliability.md).

## Порядок и границы

1. T501.1: переименование через API и кабинет, права владельца, CSRF, валидация и сохранение идентичности записи проверены на базе S03. Байтовая целостность оригинала при переименовании отдельно не проверялась.
2. После S04 — интеграция нового названия с каталогом, поиском и страницей; ручной повтор из оригинала с новым поколением.
3. После S04 — логическое удаление, отзыв выдачи, остановка FFmpeg и повторяемая очистка под общей блокировкой S04.
4. Проверки гонок, перезапуска и устойчивой отметки удаления.
5. После T602 — внешний сценарий отмены уведомления. В T802 — проверка журнала удалений при восстановлении старой резервной копии.

Проверки с остановкой процессов и удалением проводить в отдельном проекте Compose с тестовыми томами. Не закрывать весь T501 только по результату переименования и весь T503 до зависимых сценариев. S06 может начинаться после S04 и необходимых для него функций S05, без ожидания внешней проверки T503: она завершается после T602. Порядок остальных этапов сохраняется.

## T501.1 · Переименование видео

Часть общей задачи T501. API и кабинет предварительно приняты; каталог, поиск, страница просмотра, прежняя ссылка и HLS остаются непроверенными до S04. Обязательные требования всей части сохранены ниже.

- Добавить команду переименования с проверкой сессии, CSRF и владельца. Для чужого и отсутствующего ID возвращать одинаковый отказ. Принимать непустое строковое название до 200 символов после обрезки пробелов, отклонять NUL.
- Менять только название Video. Сохранить ID, ссылку, поколение, оригинал, задания и outbox. Название первоначальной загрузки и снимки уже созданных событий не переписывать.
- Добавить редактирование, сохранение, отмену, состояние ожидания и ошибку в кабинете. Сохранять введённый текст при ошибке. Выводить название текстом, без исполнения HTML.
- Проверить два аккаунта, прямой чужой запрос, отсутствие сессии и CSRF, границы длины, неверный JSON и повтор одинакового запроса.
- После S04 проверить новое название в каталоге, поиске и странице просмотра, прежнюю ссылку и воспроизведение. Под общей блокировкой строки Video отклонять переименование после DELETING; согласовать порядок с удалением.

## T501.2 · Ручной повтор обработки из оригинала

Часть общей задачи T501. Реализована локально на основе S04 из main 1d609a7 и ожидает независимого Review; push/PR/merge не разрешены в этом проходе. Проверены реальный повтор, конкурентные/запоздалые запросы, оригинал и HLS; полная отказная регрессия S04 не пройдена из-за воспроизведённого на базе orphan/flock. [Фактические результаты](homework-05/protocols/s05-reprocessing.md). T502/T503 не начинались; весь S05 остаётся незавершённым.

- Разрешать повтор владельцу после окончательного устранимого сбоя. Отказ для повреждённого или неподдерживаемого оригинала объясняет необходимость загрузить исправный файл. Не принимать повтор для активного, готового или удаляемого видео.
- **Привязать запрос к конкретному неудачному job_id**, а не только к video_id и текущему состоянию. Сохранить устойчивую связь исходного неудачного задания с созданным заданием следующего поколения; защитить связь уникальным ограничением БД.
- После проверки владельца сначала искать уже принятый повтор для этого исходного job_id. Если он существует, вернуть именно созданное задание и его текущее состояние, даже если оно уже завершилось новой ошибкой. Старый запрос не создаёт следующее поколение. Для повтора новой ошибки автор явно адресует новый failed job_id.
- Проверить оригинал под файловой защитой S04, без долгой транзакции на время чтения/хэширования. В короткой транзакции повторно проверить состояние и поколение, создать новое поколение, job, связь повтора и outbox атомарно. Сохранить ID видео, URL, байты оригинала и историю прежних попыток.
- Два параллельных запроса одного исходного job_id возвращают одно задание. Повтор публикации сообщения сохраняет message_id. Недоступность RabbitMQ не теряет принятое обязательство из outbox.
- Обработку выполнить механизмом S03–S04. Старое поколение не получает право писать или публиковать. Бюджет попыток нового задания ведётся отдельно.
- В кабинете показать допустимость повтора и переходы состояний. Сбой доставки уведомления не разрешает повторную конвертацию.

Обязательные проверки:

1. Вызвать устранимый сбой, исправить причину, повторить и получить READY без передачи файла. Сверить ID видео, URL и SHA-256 оригинала.
2. Дважды и параллельно отправить запрос с одним failed job_id: одно новое поколение, один job и одно обязательство outbox.
3. Потерять ответ первого запроса. Дождаться, пока созданное им задание тоже завершится FAILED. Повторить **старый** запрос: возвращён тот же job, новых поколения и outbox нет. Явный запрос с новым failed job_id может создать следующее поколение.
4. Проверить чужой запрос, удаление одновременно с повтором, старое сообщение, недоступный брокер и повреждённый оригинал.

## T502 · Отзыв доступа до ожидания FFmpeg

**Транзакция удаления не ждёт FFmpeg и не ждёт файловую блокировку S04.** Под короткой блокировкой строки Video проверить владельца, записать устойчивую отметку удаления, установить DELETING, отозвать поколение и сохранить обязательство очистки. Отменить ожидающие уведомления, когда их модель появится в S06. Повтор удаления безопасен.

Только **после коммита** остановить группу процессов FFmpeg и дождаться общей блокировки S04 для уборки. Новый запрос к странице, каталогу, master, вариантам и сегментам уже должен отклоняться, даже если процесс ещё завершает работу или блокировка занята. Проверка разрешения не должна ждать блокировку уборки. При недоступной БД выдача закрывается.

Остановка и уборка:

- Отправить сигнал группе FFmpeg, после ограниченного ожидания — принудительное завершение. Доказать отсутствие писателя; при неопределённости не запускать конкурентную уборку и сохранить диагностируемый DELETING.
- Под общей стабильной блокировкой S04 повторно проверить удаление и убрать оригинал, временные файлы, processing и ready. Не удалять активный lock-файл и не менять порядок блокировок вопреки S04.
- Отсутствующие файлы считать нормальным результатом повторной уборки. При ошибке оставить доступ закрытым, обязательство сохранённым и выполнить повтор после исправления причины.
- Перевести в DELETED только после завершения очистки. Историю и отметку удаления сохранить.
- Добавить подтверждение удаления в кабинете, понятный результат и состояние ожидания физической очистки.

Обязательная проверка границы: удержать общую файловую блокировку отдельным процессом, удалить ролик и подтвердить коммит DELETING. **Пока блокировка ещё удерживается**, проверить отказ новых запросов по ранее полученным ссылкам страницы, master и сегментов и отсутствие в каталоге. Затем освободить lock и проверить очистку. Уже скачанные/буферизованные байты отозвать нельзя.

Дополнительно проверить чужое удаление, удаление ожидающего/ошибочного/готового ролика, остановку записи FFmpeg и отсутствие её возобновления, прерывание и повтор уборки, ошибку прав или тома без ложного DELETED.

## T503 · Гонки, перезапуски и граница журнала

- Удалить во время FFmpeg и между rename готового каталога и коммитом READY. Любая сериализация оставляет удалённое видео закрытым; поздний результат не восстанавливает READY.
- Состязать удаление с ручным повтором и переименованием. После удаления не появляется доступный ролик или новый действующий запуск.
- Повторно доставить старую команду после удаления: она не запускает FFmpeg и не публикует результат.
- Остановить API после коммита удаления до ответа; повторить запрос. Остановить уборщик в середине очистки и перезапустить сервис. Проверить сохранность отметки в БД, закрытый доступ и завершение уборки по устойчивому обязательству.
- **Граница S05:** записать устойчивую отметку удаления и доказать её сохранение после перезапуска. Этого недостаточно для защиты от восстановления старой БД.
- **Обязательство S08:** журнал должен пережить восстановление старой БД и содержать удаления после даты backup. Согласовать независимое хранение/копирование, монотонную отметку, retention и сверку до открытия выдачи. При неполном журнале не открывать восстановленные ролики до ручной сверки. Проверку на старой резервной копии выполнить в **T802**.
- **После T602:** удалить при ожидающем и уже начатом уведомлении. Ожидающее отменить; уже начатый внешний эффект гарантированно отменить нельзя. Записанная строка остаётся историей, её ссылка закрыта. Поздний ответ не меняет удалённое видео и не запускает обработку.

## Приёмка и доказательства

- Автоматические проверки прав, CSRF, валидации, сохранения идентичности, устойчивого повтора по исходному job_id, удаления и восстановления уборки. Гонки проверять на PostgreSQL, реальном файловом томе и worker S04; доставку — на RabbitMQ.
- В браузере два автора проходят переименование, повтор после исправления причины и удаление. Проверить отмену формы, сообщение об ошибке и безопасное отображение HTML в названии.
- Проверить миграции на пустой базе и копии предыдущего этапа, сборку frontend, smoke и затронутые сценарии S02–S04.
- Записать команды, версии, ID заданий и поколений, состояния БД и результаты очистки в протокол S05. Обновить testing-report, матрицу требований и tasks по фактически выполненным проверкам. Зависимые от S04, T602 и T802 проверки сохраняют отдельный статус Not Run до выполнения.

Готовность S05 означает проверенные переименование, ручной повтор и безопасное удаление на реальном S04. Проверка внешней доставки T503 завершается после T602, восстановление по журналу — в T802; их готовность не выводится из одного перезапуска сервиса.
