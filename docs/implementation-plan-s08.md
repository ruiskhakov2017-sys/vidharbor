## 2. Target Result

1. Проверенная копия PostgreSQL, оригиналов, готовых HLS и необходимых служебных данных имеет единый backup_id, согласованную границу C, manifest и SHA-256. Копия хранится отдельно от рабочего носителя.
2. В новой среде восстановлены связи и данные; оригиналы побайтово совпадают, допустимые видео воспроизводятся. Удалённые после C ролики не открываются из старой копии.
3. Каждое незавершённое обязательство Job/Outbox/DLQ учтено: восстановлено, подтверждённо завершено либо явно изолировано до решения. Нет потерянных заданий, самовольного сброса попыток и конкурентных писателей.
4. До запуска notifier сверены события/строки/резервирования Sheets; нет дубля строки, перезаписи чужого ID или возобновления отменённой доставки.
5. Запуск, обновление и восстановление воспроизведены по инструкции; измерены полный RTO и фактический RPO относительно заранее согласованных целей.
6. AC-001–009 и применимые F подтверждены свежими доказательствами либо имеют явный FAIL/Not Run; техническая приёмка VidHarbor отделена от учебной.

### A1 · Согласованная граница PostgreSQL и медиа

| Вариант | Ограничения, риски и стоимость | Рекомендация |
|---|---|---|
| Общая пауза всех writers, pg_dump и копия медиа под удерживаемым барьером | Просто и соответствует design; downtime примерно T_dump + T_copy + T_hash. Дополнительный объём D + M и место на временные файлы. Копировать можно последовательно с низким CPU/RAM | **Предлагается для первой версии**; владелец утверждает допустимую паузу |
| Предварительное копирование + пауза и финальный проход | Меньше пауза; больше I/O, нужен проверенный учёт изменений/удалений и повторная сверка. До S04 нельзя предполагать неизменяемость всех файлов | Альтернатива после измерения долгой паузы |
| WAL/PITR и согласованные storage snapshots | Меньше пауза, но нужны snapshot-capable тома, retention WAL, согласование точек БД/FS; обычный pg_dump сам по себе PITR не даёт | Не вводить без отдельного решения о платформе/ресурсах |

Граница C определяется после завершения всех активных writers и до dump, а не временем окончания копирования. Пока барьер не снят, не работают upload, worker/FFmpeg, relay/notifier, cleanup и изменяющие запросы. Сессии/фоновые операции, пишущие в БД, также учитываются. Копируется весь выбранный медиатом: originals, ready, manifests, parts/processing и lock-структура. Частичные файлы сохраняются для диагностики, но не считаются готовыми; ОС-блокировки не «восстанавливаются» из lock-файла. Если исходник передавался, его либо завершить до C, либо зафиксировать прерывание без ложного Job/READY.

Manifest содержит backup_id, C, source SHA/image digests, версии инструментов/схемы, список/размеры/хэши, journal watermarks, состав broker backup и статус завершения. Незавершённый комплект нельзя выбирать как последний успешный. Хэши копии сравниваются с источником под паузой; сжатие не считается гарантированной экономией места.

### A2 · Журнал удалений вне восстанавливаемой БД

| Вариант | Ограничения, риски и стоимость | Рекомендация |
|---|---|---|
| Tombstones только в рабочей БД/в периодическом dump | Дешёво, но rollback старой БД теряет удаления после C | Неприемлемо для защиты старого backup |
| DB-outbox + асинхронная копия tombstones | Небольшой I/O; остаётся окно потери уже подтверждённого удаления при гибели хоста до экспорта | Допустимо только если отдельный протокол не подтверждает удаление до независимой записи |
| Долговечный append-only журнал намерений на одобренном независимом носителе до подтверждения удаления | Без нового сетевого сервиса; нужны fsync, последовательность/контроль целостности, сериализация writers, актуальный watermark и отказ удаления при недоступности носителя. J растёт с числом записей; задержка fsync входит в delete latency | **Предлагается**, но это согласуемое расширение протокола S05 |
| Отдельный удалённый журнал/WAL/PITR-сервис | Возможна лучшая изоляция отказа, но сеть, эксплуатация, credentials и возможная плата | Только отдельное разрешение владельца |

Предлагаемый протокол: под согласованной блокировкой Video записать durable deletion intent с уникальным deletion_id, video_id, поколением, монотонным номером и UTC; синхронизировать его на независимом носителе; затем коммитить tombstone/отзыв поколения/отмену доставки и подтверждать удаление. Незавершённое намерение после сбоя трактуется консервативно: ролик закрыт до сверки, а не автоматически опубликован. Цена — возможное лишнее скрытие при rollback БД; это отдельное решение владельца.

Порядок блокировок согласовать с S05: Video → короткая сериализация append журнала с её освобождением → Delivery. Уборка получает файловый lock уже после транзакции отзыва доступа; ожидание FFmpeg/уборки не удерживает эту транзакцию. Нельзя вводить обратный порядок journal → Video в другом writer.

Журнал и его доверенный текущий high-watermark не восстанавливаются назад вместе с БД. Хэш-цепочка обнаруживает повреждение, но не доказывает отсутствие потерянного хвоста: нужна сверка с актуальным независимым watermark. Неполный/устаревший/недоступный журнал блокирует выдачу. Retention обязан покрывать самый старый сохраняемый backup, удаления после него и время восстановления. Папка на том же рабочем томе или облачный snapshot этой же машины не доказывают независимость носителя.

### A3 · Job/Outbox/RabbitMQ после восстановления

| Вариант | Ограничения, риски и стоимость | Рекомендация |
|---|---|---|
| Пересоздать broker и повторить обязательства только из БД | Простая очередь, но sent_at не доказывает наличие сообщения. Raw malformed/poison DLQ могут существовать только в RabbitMQ и потеряться | Недостаточно без доказанной сохранности всех таких данных в БД/отдельном журнале |
| Только холодная копия RabbitMQ вместе с БД/медиа | Сохраняет сообщения, но требует остановки broker, того же node identity/cookie/совместимой версии; не отменяет сверку Job/Attempt и дедупликацию | Возможный вариант, не считать автоматическим восстановлением приложения |
| БД как источник обязательств + холодная broker-копия для аудита и необратимых к БД сообщений | Больше B на носителе и временный quarantined broker при сверке. Старый broker запускается только изолированно; raw DLQ сохраняется, рабочие команды восстанавливаются через действующий протокол S03 | **Предлагается для согласования**; без новых внешних сервисов, но с дополнительными локальными ресурсами |
| Надёжный журнал всех сообщений до ack | Позволяет логическое восстановление без физических broker-данных; требует изменения S03 и проверки нового протокола | Не добавлять молча |

Definitions не содержат тела сообщений и не заменяют backup RabbitMQ. Холодная копия делается после остановки publishers/consumers и закрытия каналов, затем broker; версия, hostname/node name и безопасные references на cookie/credentials фиксируются. Cookie и dump никогда не попадают в Git/публичный лог.

Сверка по Job/поколению/attempt/message_id:
- QUEUED/RETRY_WAIT активного поколения: восстановить обязательство с исходными ID/снимком и due time, даже если старая outbox имеет sent_at. На новом пустом broker отметку старой отправки не считать доказательством доставки.
- PROCESSING/RUNNING: убедиться, что старого writer нет; под lock проверить manifest S04. Полный текущий результат принимается только действующим recovery-протоколом S04. Иначе использовать worker_lost/ограниченные повторы S03, сохраняя историю и бюджет; не обнулять attempts.
- SUCCEEDED/READY не перекодировать повторно. Несовпадение файлов — нарушение целостности, а не повод незаметно сбросить состояние.
- FAILED и DLQ: сохранить terminal_event_id, историю и оригинальный raw payload там, где он не выводится из БД. Не запускать malformed или окончательно ошибочную команду как обычную работу.
- DELETING/DELETED и отозванные поколения: не создавать активные задания и не публиковать результат.
- Повтор сверки должен быть идемпотентным. Допустима повторная доставка того же сообщения; недопустимы новый Job/поколение без причины и два FFmpeg в одной папке.

Для каждого обязательства нужен итоговый реестр: восстановлено/завершено/изолировано с причиной. Изоляция не скрывает потерю: неразрешённая неоднозначность блокирует соответствующую готовность и полную приёмку T802.

### A4 · Sheets: event_id, строка и аллокатор

| Вариант | Ограничения, риски и стоимость | Рекомендация |
|---|---|---|
| Довериться только старой карте в restored PostgreSQL | Минимум работы, но занятые после C строки и старые незавершённые запросы могут столкнуться с новой выдачей номера | Неприемлемо |
| Прочитать всю выделенную вкладку и поднять границу | Нужны доступ/квоты/сериализация. Пустая строка может быть зарезервирована запросом, который ещё выполняется; одного max заполненных строк недостаточно | Часть сверки, не самостоятельная гарантия |
| Независимый durable ledger резервирований + read-only сверка Sheets | Малый рост L на событие и дополнительный fsync; требуется изменение аллокатора S06 и сохранение reservation до внешнего запроса | **Предлагается**, после отдельного утверждения; можно использовать одобренный носитель A2 с отдельным потоком |
| Новый непересекающийся диапазон/вкладка для restore epoch | Ручное выделение диапазона и хранение его границы вне старой БД; меняет конфигурацию интеграции и требует разрешения на Sheets/n8n | Резервная альтернатива владельца, не автоматическая подмена |

Notifier выключен; старые процессы исключены, состояние уже начатых n8n-запросов учтено. Сверять весь закреплённый диапазон, event_id, snapshot полей и durable reservations, а не только последние строки. Нижняя граница аллокатора после restore выше всех сохранённых, наблюдаемых и ещё зарезервированных номеров, включая пустые.

Тот же event_id/строка/снимок допускает повтор после потерянного ответа; чужой ID или иные данные дают конфликт без перезаписи. Внешняя строка события, отсутствующего в старом backup, остаётся историей: из неё нельзя выдумать восстановленное видео или READY. Повторы не создают Job и не запускают FFmpeg. При непрочитанной таблице, неизвестных reservations или старых in-flight эффектах notifier остаётся выключенным. Проверки модели получателя не закрывают реальную AC-007.

### A5 · Безопасное открытие доступа

| Вариант | Ограничения, риски и стоимость | Рекомендация |
|---|---|---|
| Поднять весь Compose после pg_restore | Просто, но гонки writers, повторных webhook и выдача удалённого/частичного HLS до сверки | Неприемлемо |
| Ручная последовательность остановленных сервисов | Без нового компонента, но легко забыть один процесс или открыть старую ссылку | Дополнительная процедура, не единственная защита |
| Закрытый по умолчанию restore-mode с отдельными gate HTTP и notifier + поэтапный запуск | Нужны явные guards readiness/выдачи и проверяемый отчёт; почти нет дополнительного постоянного CPU/RAM. Это изменения приложения/конфига будущего этапа, не уже существующая возможность | **Предлагается для согласования** |

Последовательность: CLOSED → DB+files verified → deletions applied → jobs reconciled → внутренние функциональные проверки → публичная выдача разрешённых видео → notifier после A4. Имена — состояния будущей процедуры, не текущая модель приложения. При недоступной БД, неполном журнале, неверном manifest или поколении выдача закрыта; liveness процесса может оставаться 200, readiness/публичная выдача — нет.

Gate публичной выдачи и gate notifier независимы: отказ n8n/Sheets не закрывает уже проверенное READY-видео (NFR-004). Отказ broker отражается на готовности worker/relay, а не сам по себе на каталоге. Неопределённое задание/поколение остаётся закрытым; полная приёмка restore требует разрешить все обязательства, даже если часть проверенных видео уже доступна.

Проверить прямые старые ссылки на master/варианты/сегменты, обход страницы, кэш и запрос во время удерживаемого lock уборки. Новые запросы должны закрыться сразу; уже скачанные/буферизованные байты отозвать нельзя. Повреждённое восстановление не подменяет рабочие тома и не вызывает автоматический fail-open.

### A6 · Ресурсы, RPO/RTO и носитель

Владелец утверждает модель отказа, носитель/его реальную независимость, retention, допустимую паузу, RPO/RTO, CPU/RAM/диск и окно большого прогона. Конкретные цены/ёмкости и время заранее неизвестны; плата за облако/новый сервис не предполагается. Существующий одобренный физический носитель дешевле по изменениям системы, но его закупка/потеря вместе с хостом остаются отдельными рисками.

Обозначения: M — выбранные медиа; D — dump; B — холодные broker-данные; J/L — журналы; R — reserve, заданный по измерениям. Носитель backup должен вместить retention копий (D+M+B+manifest) плюс J/L и R. Для restore нужны M + оценка восстановленной БД и временных индексов/WAL + broker-данные/карантин + R; локальная staging-копия архива считается отдельно. Свободное место рабочего тома должно покрыть пиковый прирост parts/original/processing/ready и dump staging, а не только размер входного файла.

Не считать место свободным из-за сжатия или дедупликации до измерений. Измерить реальный I/O и оценить T_dump+T_copy+T_hash; начинать последовательно: один FFmpeg, pg_restore --jobs=1, одно хэширование. Параллельность увеличивать только по измерениям. Проверить, что контейнерные CPU/RAM limits действительно действуют, особенно при rootless Docker без cgroups.

Технические бюджеты FFmpeg/AMQP из S03–S04 сохраняются; трёхчасовой кандидат на попытку не превращается в продуктовый лимит длительности. Если большой образец не укладывается, согласовать ресурсы/технический бюджет и повторить, а не урезать вход или объявлять PASS.

RPO измеряется относительно последнего восстановленного подтверждённого бизнес-изменения и времени сбоя; время завершения копирования не является границей C. RTO — от начала недоступности/объявления восстановления, включая проверки и ручную сверку; отдельно записать RTO публичной выдачи, полного восстановления и длительности БД/медиа/согласований. Владелец определяет целевые пороги обоих RTO; открытие только HTTP не считается восстановлением всей интеграции. Для подтверждённых удалений требуется сохранность независимого журнала в согласованной модели отказа; это не обещание нулевого RPO для всех данных.

## 6. Testing Strategy

### Будущие команды и воспроизводимость

Нотация S08 <команда> в §3 означает **предлагаемый, пока не реализованный** интерфейс:

Названия CLI фиксируют проверяемый контракт, не утверждают существование кода; создать helper/guards можно лишь после утверждения архитектуры.

### Набор проверок

1. Сначала малые fixtures: нормальный original/READY, незавершённая part, PROCESSING, RETRY_WAIT, FAILED/DLQ, неподтверждённая Delivery/SENDING, удалённое после C видео. У каждого известны ID/поколение/хэши.
2. Отказы: остановка между dump и media copy; битый/неполный backup; journal без хвоста; сбой после durable intent до DB commit; старая команда после удаления; живой старый FFmpeg; повтор reconcile; отсутствие target queue/DLQ; несовместимая схема.
3. Sheets: ответ потерян после успешной записи, два разных ID на строку, резервирование пустой строки старым in-flight запросом, внешняя строка после C без восстановленного Video. Реальные изменения только в одобренной учебной вкладке с отдельным разрешением.
4. Gate: попробовать прямые старые ссылки до каждого открытия, при недоступной БД, при занятом cleanup lock и после повторного запуска. Ошибка не должна открывать доступ.
5. Затем большой исходник 3–5 ГБ в пределах 5 ГиБ: измерить не только размер dump, но upload/очередь/FFmpeg/HLS/restore и отзывчивость. Остановить по согласованным ресурсным порогам без стирания исходника.
6. Полные AC и P: проверить до и после restore, включая Chrome, Edge и Firefox, реальные качества/Auto/manual, логи, trace, метрики и dashboard.

Журнал каждого прогона: SHA/версии/конфигурационные имена, UTC начала/конца, backup_id и C, ID событий/заданий, команды/exit code, ожидаемое/фактическое поведение, PASS/FAIL/Not Run, причина и безопасные логи. Сохранять exit исходной команды, не маскировать ошибку pipe/formatter. Нулевой набор тестов — не PASS. Старые журналы/скриншоты не выдавать за текущие; секреты, cookie, dump и raw DLQ не публиковать в отчёте.

## 8. Risks & Recovery

| Риск | Предотвращение/реакция | Что запрещено считать восстановлением |
|---|---|---|
| ENOSPC/RAM/CPU/time budget | Preflight каждой фазы, reserve, один worker, контролируемая пауза; сохранить originals/диагностику, исправить ресурс и повторить затронутое | Урезанный без согласования файл или отключённая проверка hash |
| Несогласованные dump/медиа | Барьер A1 удерживается до полного комплекта; недокопированный backup помечен неготовым | Независимые копии разных моментов без протокола |
| Утрата журнала/хвоста или stale watermark | Закрытая выдача; восстановить authority/сверить вручную с полными доказательствами | Публикация старых роликов на основании только старой БД |
| Повреждённый backup/носитель | Отклонить комплект, использовать другой проверенный; исходные данные не удалять | Успех списка dump при нечитабельных данных |
| Старый worker/notifier жив | Изоляция старой среды, fencing поколений/lease и lock S04; не запускать нового писателя при неопределённости | Очистка папки под живым FFmpeg или доверие одному новому token |
| Job утрачен/повторён опасно | Реестр A3, исходные ID, история attempts, проверка manifest и реальной DLQ | Безусловный reset sent_at/attempts, перепубликация всех Job, запуск malformed |
| Sheets/credentials/доступ недоступны | Notifier выключен; согласование доступа отдельно; без значений secrets в чате | Append вместо фиксированной строки или перезапись чужого event_id |
| Обновление несовместимо с данными | Проверить на копии; сохранить до-update backup; возвращать только совместимую пару код/БД или выполнить проверенный restore | Автоматический reverse любой миграции |
| «Отдельная папка» теряется вместе с хостом | Владелец утверждает физическую независимость/модель отказа и доступность после потери хоста | Вторая папка на том же томе как единственная копия |
| Преждевременный gate/open или недоступная БД | Закрытая по умолчанию выдача и отдельно notifier; проверить кеш/прямые сегменты | Liveness=200 как разрешение публичной выдачи |

При неуспехе не удалять исходный стенд и рабочие тома. Очистка допустима только для подтверждённых disposable target-проектов после сохранения доказательств и явной проверки label/имён. Ни recovery-helper, ни инструкция не должны выполнять destructive действие над source по умолчанию.
