## 1. T601 · Доступ и контракт

1. Подтвердить адрес HTTPS n8n, доступ к выделенной вкладке и открытие плейлиста из среды получателя.
2. Проверить поддержку исходного тела запроса, HMAC-SHA-256 и безопасного хранения общего секрета. Альтернативный способ защиты согласовать при ограничениях установки.
3. Согласовать формат события и подтверждения, таймауты и пять попыток в пределах часа.
4. На отдельном тестовом получателе проверить подлинный запрос, неверную/просроченную подпись и конфликт строки. Действующий workflow менять только после отдельного разрешения.

Контракт события — [reliability](homework-05/reliability.md#webhook-и-стабильная-строка).
Заголовки реализации: X-VidHarbor-Timestamp (Unix seconds), X-VidHarbor-Signature (hex HMAC-SHA-256 от timestamp + "." + raw body). Допуск часов тестового получателя — 300 секунд. Каждая попытка заново подписывает неизменённый снимок с актуальным временем. Секрет — минимум 32 байта, из файла; значения не пишутся в код или логи.

## 2. T602 · Доставка существующего события

S04 в транзакции перехода в READY уже создаёт **Outbox kind=video.ready**: стабильный message_id/event_id и неизменённый снимок данных публикации. S06 не меняет эту транзакцию и не создаёт новый ID. `attach_existing_ready` под Video lock подключает отдельный ReadyEvent (source OneToOne на этот Outbox) и Delivery, добавляя только транспортный sheet_row.

Номер строки выделяет S06: общий SheetAllocator под select_for_update и fsync reservation в отдельном журнале до DB commit. Резервирование содержит event_id/row/digest исходного snapshot; после rollback/restore строка не переиспользуется. Повтор attachment возвращает прежнюю reservation. ReadyEvent уникален по video/generation и строке, со второй строки после заголовка. Это фактическая интеграция с существующим S04, а не требование переписать S04 ради аллокатора.

Отправитель:
- проверяет идентичность event_id, video_id, sheet_row снимка;
- в одной транзакции блокирует Video, затем Delivery, проверяет READY и generation и захватывает доставку;
- отправляет HTTP вне транзакции, с ограничением DNS ожидания и socket timeout 5 секунд (не общий hard deadline всей HTTP-операции), без перенаправлений; точный allowlisted hostname, все DNS/IP должны быть публичными, соединение закреплено за проверенным IP с исходным TLS hostname; ambient proxy не используется;
- принимает только HTTP 200 с JSON {"event_id":"<тот же UUID>","status":"written"};
- не изменяет задания обработки, оригиналы или состояние публикации.

Получатель должен последовательно выполнять чтение, проверку принадлежности и запись для одного номера строки. Одного values.update недостаточно: два разных ID могут увидеть пустую строку. Для n8n нужен устойчивый к перезапуску механизм сериализации, охватывающий все конкурирующие выполнения и сам вызов Sheets. При разных ID один записывается, второй получает конфликт. При том же ID повтор записывает прежние значения в прежний диапазон. Режим Sheets — RAW, append не используется. Подтверждение отправляется только после успешной записи. Рабочая вкладка защищена от сортировки и переноса строк.

Тестовый получатель использует ReceiverRow в PostgreSQL. Создание уникальной строки и SELECT FOR UPDATE сериализуют проверку и запись, включая разные ID и несколько HTTP-потоков. Это модель контракта, а не реализация Google Sheets или доказательство корректности workflow n8n.

## 3. T603 · Повторы, lease и ручное восстановление

График реализации — 0/1/5/15/45 минут от первой попытки; максимум пять захватов в час. Таймауты, неверное подтверждение, 429 и 5xx повторяются. Retry-After учитывается, но не продлевает окно за час. Остальные HTTP-ошибки, включая конфликт, требуют исправления и ручного повтора.

Состояния Delivery: PENDING, SENDING, WRITTEN, FAILED, BLOCKED, CANCELLED.
- SENDING имеет lease на 60 секунд и случайный token.
- После падения и истечения lease другой процесс может повторить отправку с прежним событием, данными и строкой, если видео ещё доступно.
- Каждый захват расходует попытку, даже если процесс упал до HTTP. После пятого захвата требуется ручное восстановление.
- Завершить попытку вправе только процесс с текущим token. Запоздалый ответ старого процесса не подтверждает новую попытку.
- Ручной повтор разрешён для FAILED/BLOCKED, сбрасывает автоматический бюджет, но сохраняет событие, снимок, строку и общий счётчик попыток.

## 4. T503 · Удаление и гонки

S05 обязан использовать ту же блокировку Video и порядок Video → Delivery:
1. Начать транзакцию и SELECT FOR UPDATE Video.
2. Отозвать READY/поколение и вызвать cancel_locked(video).
3. Зафиксировать удаление и отмену доставки вместе.

Если удаление выиграло блокировку, отправитель не получает захват. Если отправитель уже получил право начать запрос, внешний эффект может произойти: записанная строка остаётся историей, ссылка закрывается средствами S05. Завершение старой попытки не отменяет CANCELLED. После перезапуска отменённая доставка не возобновляется. Сам cancel_locked проверяет наличие транзакции; обязанность захватить Video лежит на S05.

## 5. Запуск и проверка

Зависимости остаются в api/requirements.txt. Сначала применить миграции 0003 на тестовом стенде.

Внутри контейнера приложения, из /app:
```sh
python manage.py migrate --noinput
python manage.py test vidharbor.test_notifications vidharbor.test_job_attempts vidharbor.test_relay --noinput
```

Отдельный тестовый получатель, в том же контейнере/сетевом пространстве:
```sh
python manage.py test_ready_receiver --secret-file /run/secrets/webhook_secret
```

Отправитель для локального теста:
```sh
python manage.py notify_ready --url http://127.0.0.1:8096/video-ready --allow-host 127.0.0.1 --allow-test-loopback
```

Рабочая конфигурация:
```sh
python manage.py notify_ready --url https://n8n.example.invalid/webhook/video-ready --allow-host n8n.example.invalid
python manage.py notify_ready --retry <event-uuid>
```

Адрес выше — пример. Секрет по умолчанию читается из /run/secrets/webhook_secret. Подключить его через отдельную локальную конфигурацию, не коммитить значения. Автозапуск отправителя в основной Compose пока не включён: нужны S04–S05 и подтверждённый получатель. --once выполняет один проход и максимум одну отправку.

После восстановления старой БД держать отправитель выключенным до сверки event_id, строк и верхней границы аллокатора. Это обязательная интеграционная процедура S08.

Автоматические проверки на PostgreSQL и настоящем локальном HTTP:
- пять попыток, окно часа, Retry-After, ручной повтор;
- неизменность снимка после переименования;
- восстановление lease и отказ устаревшему token;
- два одновременных отправителя — один захват;
- удаление до захвата, после захвата и истечение lease для недоступного видео;
- два разных ID за одну пустую строку, включая параллельные HTTP-запросы: один успех и один конфликт;
- повторы одного ID и потеря ответа после записи: одна строка;
- неверная/просроченная подпись, неправильный ack, запрещённый адрес;
- отсутствие повторного задания перекодирования.

Для завершения S06 отдельно проверить настоящий путь VidHarbor → n8n → Google Sheets с плейлистом S04 и удалением S05. Подтвердить единственную строку, доступность ссылки получателю, отказ Sheets, потерю ответа, параллельные разные ID и закрытие ссылки после удаления. До этого T601–T603 и связанная часть T503 целиком не отмечаются выполненными.
