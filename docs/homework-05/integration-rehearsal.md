# Учебная интеграция n8n / Google Sheets: пакет подготовки

Статус: **подготовлено, внешний прогон Not Run**. Ни workflow, ни таблица не создавались и не изменялись. Основа — существующий S06, [контракт надёжности](reliability.md), [notifications.py](../../api/vidharbor/notifications.py), [test receiver](../../api/vidharbor/test_receiver.py). Тестовый PostgreSQL ReceiverRow не является Google Sheets. Это инструкция для отдельного согласованного подключения, не команда включить текущий notifier.

## Точный контракт отправителя

`POST` в точный HTTPS URL из allowlist. HTTPS hostname должен совпасть; все DNS-ответы проверяются на публичный IP, соединение закрепляется за проверенным адресом с TLS hostname verification. Private/loopback/link-local адреса, redirect и ambient HTTP proxy запрещены. Единственное исключение — явный loopback test mode в существующих тестах. Не разрешать внутренний адрес n8n обходом проверки; сначала согласовать доступный учебный endpoint.

Payload: ровно восемь полей из [синтетического примера](../../config/integrations/video-ready.example.json). `type=video.ready`, целочисленный `version=1`, UUID `event_id`/`video_id`, непустой title ≤200 символов, `ready_at` с UTC offset 0, playlist URL до `master.m3u8`, целый `sheet_row>=2`. Пример с `.invalid` предназначен только для проверки формата и не открывается в сети. Историческая дата примера не является timestamp подписи.

S04 уже создал Outbox/event_id вместе с READY. S06 не создаёт новое событие и не запускает конвертацию. Строка закрепляется durable reservation. Body: UTF-8 JSON, `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')`. При повторе прежние body/event_id/row/title/ready_at/URL неизменны; новое название после публикации не переписывает snapshot.

Headers: `Content-Type: application/json`, `X-VidHarbor-Timestamp` — целые epoch seconds UTC, `X-VidHarbor-Signature` — lowercase hex HMAC-SHA256:

```text
HMAC_SHA256(secret_bytes, timestamp_ascii + b'.' + original_raw_body)
```

Новая подпись для каждой попытки. Не пересобирать JSON перед проверкой: использовать raw bytes. Сравнение constant-time; рассинхронизация часов допускается до 300 с в тестовом получателе. Секрет ≥32 байт, отдельный private file `webhook_secret`, не env value/скриншот/execution log. Шаблон без credentials: [notifications.env.example](../../config/integrations/notifications.env.example).

Успех — **HTTP 200** и JSON **ровно** `{"event_id":"<тот же UUID>","status":"written"}` после подтверждённой записи либо чтения уже совпадающей строки. ACK ≤4096 байт. 202/204, неправильный ID, лишние поля, не-JSON, большой ACK — не успешное подтверждение. HTTP timeout 5 с. 429/5xx и transport/invalid ACK → retry; прочие HTTP ошибки, включая 409/redirect → BLOCKED. Retry-After учитывается для 429/5xx, но не продлевает окно бесконечно.

Пять попыток запланированы относительно начала цикла: 0/1/5/15/45 минут, максимальное окно 1 час; учитываются Retry-After и реальное время ответа. SENDING lease 60 с, token fencing не даёт старому процессу подтвердить новую lease/отменённую доставку. После истечения lease возможна повторная HTTP-доставка, поэтому идемпотентность получателя обязательна. Управляемый повтор сохраняет event_id/body/row и total_attempts, не сбрасывает бизнес-Job.

## Что согласовать до подключения

1. URL/hostname/версию n8n, владельца и доступ к **отдельному учебному** workflow и вкладке; список источников запросов/HTTPS; секрет передать вне Git/чата.
2. Доступную получателю публичную HLS-ссылку нового события. Старый loopback URL в immutable snapshot нельзя молча заменить; для новой публичной проверки загрузить отдельный учебный ролик после правильного PUBLIC_BASE_URL.
3. Схему колонок и сериализацию записи. Предлагаемая учебная схема A:H: event_id, video_id, title, ready_at UTC, playlist_url, type, version, sheet_row; строка 1 — header. Это предложение, не изменение таблицы. Фактический диапазон и способ безопасной записи согласовать до запуска.
4. Правила execution-log retention в n8n: тела содержат названия видео; исключить секреты/raw подписи и ограничить персональные данные. Не выдавать публичный доступ к таблице.

## Порядок создания после отдельного разрешения

Создать отдельную вкладку, ограничить Google credentials этой таблицей. Получить raw body в n8n Webhook, проверить размер/подпись/timestamp/schema, затем войти в **одну последовательную секцию для sheet_row**. Внутри прочитать закреплённую строку, сверить ID и весь snapshot, записать конкретный диапазон через `values.update` с `valueInputOption=RAW` (защита от формул из title), перечитать и сверить значения, только затем ответить ACK. Пустая строка → запись; тот же ID и snapshot → прежний ACK; другой ID или другие данные →409 без перезаписи. Не применять append/поиск следующей пустой строки и не переназначать row при ошибке.

**`values.update` не предоставляет compare-and-swap.** Read/check/update без сериализации небезопасны: разные ID могут одновременно увидеть пустую строку. Простого process mutex и двух независимых n8n SQL nodes недостаточно. Для отдельного учебного n8n возможен один действительно последовательный production execution, если версия/режим/edition это поддерживает и все writers, включая manual/retry, проходят тот же барьер. Нельзя менять concurrency действующего общего n8n без разрешения. Альтернатива — durable keyed admission/lock в уже согласованной БД с удержанием одной сессии на весь цикл; это отдельное архитектурное решение, а не якобы готовый workflow.

До выбора и проверки этого барьера интеграция **не готова к приёмке**. На crash/restart нужно fence старые executions и незавершённые Google-запросы; после неизвестного исхода сначала прочитать строку и сопоставить event_id, не открывать параллельную запись другого ID. Google API не умеет fencing token в values.update: даже истёкшая локальная lease не отменяет старый удалённый запрос. Если нельзя доказать отсутствие позднего запроса, строка остаётся в карантине до ручного разрешения. Не обещать exactly-once HTTP; цель — идемпотентный видимый эффект.
