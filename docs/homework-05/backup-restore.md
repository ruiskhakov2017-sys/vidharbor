# Копирование и восстановление VidHarbor

Статус на 2026-11-15: **проверен изолированный учебный стенд на одном облачном хосте**. Это не доказательство восстановления после потери хоста. Постоянный независимый носитель, retention, целевые RPO/RTO и production A1–A6 остаются на согласовании. Основание — разрешение владельца на короткую паузу записи и чистое восстановление. [Результаты и доказательства](protocols/s05-s08-completion.md).

## Что составляет копию

`scripts/s08.py backup` останавливает web/API/upload/worker/relay/notifier/cleanup и проверяет migrate, проверяет отсутствие работающих писателей и фиксирует границу снимка. PostgreSQL остаётся доступным только оператору внутри сети. Внешние писатели и доступ других операторов должны быть исключены до запуска: инструмент не является распределённым барьером для неизвестных процессов.

Комплект содержит `postgres.dump` (`pg_dump -Fc --no-owner`), `media.tar`, холодный `rabbitmq.tar`, `snapshot.json` и `manifest.json`. Снимок перечисляет каждый файл с размером/SHA-256 и записи Upload, Video, Job, Attempt, Outbox, ReadyEvent, Delivery, ReceiverRow и SheetAllocator. Дамп также содержит остальные таблицы PostgreSQL, включая учётные записи. Manifest фиксирует образы, HEAD исходников, контрольные суммы, время границы, полноту и длительность паузы. При грязном рабочем дереве одного HEAD недостаточно — сохранить проверяемый diff отдельно.

Журнал удалений и резервирований строк хранится в отдельном `journal_data`: цепочка SHA-256, sequence, fsync и head watermark. Он **не откатывается вместе со старой БД**. Перед restore нужен отдельный свежий экспорт `current-authority.tar` и его metadata. При повреждении/расхождении хвоста доступ закрыт. Файловая цепочка обнаруживает повреждение, но сама не доказывает независимость носителя или отсутствие согласованного отката журнала и watermark; для production это открытое A2/A6.

Копии содержат персональные данные, хэши паролей и broker cookie. Каталог держать закрытым, шифрование и внешний перенос согласовать отдельно. Не добавлять копии, session/cookie JSON, ключи и секреты в Git или review-архив.

## Конфигурация отдельного стенда

Сохранить JSON вне репозитория; пути заменить фактическими. Source и target должны иметь разные имена проекта, порты и собственные тома. Названия начинаются с `vidharbor-`. В `compose_files` перечислить абсолютные пути основного файла и только необходимых облачных override. Секреты — отдельные файлы, для холодной копии RabbitMQ сохранить исходные credentials/identity и закреплённый образ.

```json
{
  "reports": "/workspace/private-drill/logs",
  "backup_root": "/workspace/private-drill/backups",
  "source": {
    "project": "vidharbor-source-drill",
    "compose_files": ["/workspace/vidharbor/compose.yaml"],
    "env": {
      "VIDHARBOR_PORT": "8181",
      "VIDHARBOR_PUBLIC_BASE_URL": "http://127.0.0.1:8181",
      "VIDHARBOR_SECRETS_DIR": "/workspace/private-drill/secrets"
    }
  },
  "target": {
    "project": "vidharbor-target-drill",
    "compose_files": ["/workspace/vidharbor/compose.yaml"],
    "public_alias_port": 8181,
    "env": {
      "VIDHARBOR_PORT": "8182",
      "VIDHARBOR_PUBLIC_BASE_URL": "http://127.0.0.1:8181",
      "VIDHARBOR_SECRETS_DIR": "/workspace/private-drill/secrets"
    }
  }
}
```

`public_alias_port` — только локальный учебный cutover: после остановки source target получает его старый loopback-порт. Так неизменённые абсолютные playlist URL из события продолжают работать. Для настоящего домена/TLS нужен отдельный согласованный план переключения; инструмент его не выполняет.

## Команды процедуры

Из корня проверяемой версии, с установленными Docker/Compose и Python 3:

```bash
python3 scripts/s08.py --config /workspace/private-drill/config.json preflight
python3 scripts/s08.py --config /workspace/private-drill/config.json backup --bundle /workspace/private-drill/backups/run-01 --resume
```

Успех — exit 0, `complete=true`, `source_resumed=true`, читаемые компоненты и manifest. В ходе проверки границы остановка всех перечисленных писателей обязательна. До начала зарезервировать место для исходника, HLS, копии, второго набора томов и запаса БД/broker; текущая оценка скрипта не заменяет проверку Docker data-root, quota и свободного места на каждом реальном mountpoint. Проверить `docker info`, `df`, CPU/RAM и наличие действующих cgroups.

Для проверки старой копии: возобновить source, удалить через API ролик из снимка, проверить отказ старых URL, затем снова остановить **все** source writers. Для обычного восстановления этот искусственный шаг не нужен. `fence` сохраняет receipt с прежними restart policies, меняет их на `no` только у writers выбранного source и останавливает также контейнеры в restart loop. Простого stop недостаточно: после перезапуска Docker старые writers могли автоматически ожить, что реально наблюдалось при возобновлении облачной среды. Restore/open теперь дополнительно проверяют этот барьер. Не выполнять `compose up` source: он может заново применить исходные restart policies. Receipt не является защитой от действий другого администратора.

```bash
python3 scripts/s08.py --config /workspace/private-drill/config.json fence
python3 scripts/s08.py --config /workspace/private-drill/config.json export-journal --authority /workspace/private-drill/current-authority.tar
python3 scripts/s08.py --config /workspace/private-drill/config.json restore --bundle /workspace/private-drill/backups/run-01 --authority /workspace/private-drill/current-authority.tar
```

Restore отказывается совпадать с source, работать при живом старом writer, перезаписывать существующий PostgreSQL/media/broker/journal том, принимать неполный bundle, несовместимые образы, неверные хэши, ссылки/выходы за каталог в tar или устаревший журнал. Создаётся новая PostgreSQL; перед `pg_restore --exit-on-error --no-owner --jobs=1` проверяется отсутствие таблиц public. Не использовать `--clean` против действующей БД.

До открытия target работает с `RESTORE_MODE=1`: публичные API/страницы/HLS отвечают 503, writers не запускаются. Сначала сверяются записи и **все** файлы, затем применяется свежий deletion authority. Проверить удалённые watch/master/варианты/сегменты: 404 после открытия. Исходник и остатки HLS удаляются под прежним flock; при незавершённой очистке открывать доступ нельзя.

## Согласование заданий и внешних эффектов

`recovery reconcile` проверяет READY manifest и существующие Job/Outbox; для учтённой активной команды снимает sent_at только с её конкретного ID. Job, generation, message_id, счётчик и история Attempt сохраняются. Холодная копия RabbitMQ сохраняет raw DLQ; дубли с тем же ID допустимы, новая конвертация завершённой команды — нет. Не очищать очередь и не переотправлять весь Outbox без разбора. Старые worker/FFmpeg должны оставаться изолированными.

Для событий сверяются исходный Outbox, неизменённый snapshot, закреплённая строка и digest независимой reservation; аллокатор поднимается выше всех резервирований, включая отсутствующие в старой БД. Расхождение — отказ, вся транзакция reconcile откатывается. После restore `SENDING` восстанавливается по истечении lease с тем же ID/строкой; удалённые события отменяются. Уже записанные исторические строки не удаляются.

**Реальная Sheets пока не сверялась.** БД и локальный тестовый получатель не доказывают состояние внешней таблицы или завершение in-flight n8n. Notifier остаётся выключенным (опциональный Compose profile). До его отдельного открытия: согласовать учебный workflow/вкладку, доступную ссылку, прочитать event_id/строки, учесть поздние запросы, разрешить конфликты без перезаписи чужого ID и только затем согласовать запуск notifier. Не считать профиль полноценным production gate от ошибочной команды оператора.

После успешного закрытого restore:

```bash
python3 scripts/s08.py --config /workspace/private-drill/config.json open
```

Команда проверяет отчёт верификации и остановку source, открывает **только** проверенный локальный target и запускает его relay/worker/cleanup; notifier не запускается. Config получает локальный ports override. Не запускать прежний source поверх этого адреса. Проверить готовность, старые ссылки, оригинал, восстановленное задание, DLQ и новый номер строки с тестовым получателем (`scripts/verify_restore.py --help`). Отчёт должен иметь PASS по всем реально выполненным условиям; неподтверждённые внешние проверки оставить Not Run.

## Отказ и измеренный результат

При любом отказе restore оставить gate закрытым и сохранить логи. Инструмент не удаляет частично созданные тома: разбирать их отдельно, новый прогон выполнять под новым явно изолированным именем. При сбое backup проверить `manifest.json` и фактический список работающих сервисов; автоматически завершённый комплект не означает успешное возобновление source. Возвращать только прежние writers и только при отсутствии открытого target. Возврат старой БД не отменяет актуальный журнал удалений.

Факт учебного прогона: пауза **79.193 с**, восстановление **106.147 с**, отдельное открытие **23.710 с**. Сверены 98 файлов, включая оригинал 3,529,596,888 байт. Удаление после snapshot пережило восстановление старой БД. Целевые RPO/RTO ещё не заданы; сумма отдельных таймеров не является полным RTO с ручными паузами и внешними проверками. RPO для катастрофы хоста и долговечность внешнего носителя не измерялись.

## Независимый носитель: подготовленные варианты, не внедрение

Дополнение S07 от2026-11-16. Принятый S08 drill не повторялся и не переписывался. Данные и rollback-recovery удаления из main сохранены. Локальный `journal_data` переживает rollback PostgreSQL и восстановление старого dump **на сохранившемся хосте**; он не переживает потерю диска/всей машины автоматически. Второй каталог/volume той же машины не является независимой копией.

| Вариант | Копии и журнал / ресурс | Цена и безопасность | Ограничение восстановления |
|---|---|---|---|
| Отдельная машина/NAS с POSIX filesystem | Полные bundles по защищённому каналу; для authority нужен синхронный удалённый durable barrier/fsync с доказанной семантикой носителя | Отдельный host/storage, GB×месяц, трафик, администрирование/шифрование. Конкретная цена/провайдер не выбраны | Независимый failure domain и актуальный watermark обязательны. NFS mount сам по себе не доказывает fsync/защиту от rollback. Текущий append пишет локально; удалённый протокол не реализован |
| Версионируемое object storage | Зашифрованные bundles+manifest; отдельные append-only records/head для delete и reservations; по возможности immutability | GB×месяц + PUT/GET + egress; версии/retention увеличивают объём; отдельные least-privilege credentials и ключ вне backup | Асинхронная выгрузка имеет ненулевое окно потери хвоста. Нет готового atomic POSIX append/fsync: нужен согласованный протокол conditional head/проверки полноты. Не подключать как обычный каталог без проверки |
| SSH/SFTP на независимый сервер оператора | Периодическая шифрованная копия+checksum/manifest и отдельно проверяемый export authority | Имеющийся независимый сервер может уменьшить дополнительные расходы; остаются storage/traffic/admin. SSH host key verification, отдельные права | Достаточно для резервных bundles, но периодический export журнала не даёт нулевой потери удалений при гибели source. Для свежего authority требуется дополнительное решение; пока gate закрыт |
| Только текущий локальный volume | Уже проверенный учебный same-host drill, без нового сервиса | Минимальные дополнительные ресурсы; общий диск/ключи/администратор | **Не production disaster recovery**: потеря машины уничтожит и оригиналы, и journal/watermark, и местные copies. Это текущая граница, не рекомендация постоянного хранения |

Цена не оценивается выдуманным тарифом: после выбора варианта запросить фактические storage/API/egress/доступность/минимальную оплату; умножить объём bundles и версий на согласованную частоту/retention. Не выбраны carrier, provider, бюджет, encryption-key custodian, retention, частота или допустимая пауза production.

Для удаления и резервирования строк потеря свежего хвоста опаснее потери нового каталога: старый dump может вновь показать удалённое видео или выдать уже занятую строку. RPO=«не больше N минут новых записей» не разрешает молча воскрешать удаления. Нужна отдельная политика durability authority. Рекомендуемый для согласования принцип A2/A4: подтверждать intent/reservation только после независимого durable барьера; при недоступности носителя либо неизвестном актуальном high-watermark — fail closed, notifier/HTTP закрыты. Альтернатива с async replication допустима только после явного утверждения окна потери и консервативного quarantine/ручной сверки. Эта удалённая семантика сейчас **не реализована и не доказана**.

RPO — максимально допустимая потеря данных по времени от инцидента назад; RTO — допустимое время до безопасно восстановленного сервиса, включая получение ключей, transfer, rebuild, проверки и открытие. Измеренные79.193/106.147/23.710 с относятся к отдельным операциям same-host drill, не являются обещанным RTO. Цели задаёт владелец; периодичность backup/репликации выбирается после целей и измерений.

## Потеря всей машины: будущий runbook и gate

До возможности такого восстановления нужны: независимый проверенный bundle, **актуальные независимо сохранённые deletion/reservation authority и watermark**, копия разрешённых secret/crypto keys вне погибшего хоста, pinned images/source SHA/Compose/env, версия/node identity/cookie RabbitMQ, ресурсы для чистых volumes, доступ к DNS/TLS и внешней сверке Sheets. Одна GitHub-копия исходников эти данные не заменяет.

После отдельного разрешения: fence прежний host/writers и все внешние in-flight requests; поднять новый изолированный target без публичных ports/notifier, проверить подписи/хэши/версии и чистую PostgreSQL, выполнить существующий restore/reconcile, проверить **все** original/HLS hashes, удаления и закрытые URL, Job/Outbox/DLQ/attempt history, event snapshot/row high-watermark. Неизвестный свежий tail →не открывать. Реальную Sheets и поздние n8n executions сверить до notifier; публичный gate открыть по утверждённому отчёту, notifier отдельно. Затем измерить полный RTO и фактическое окно RPO на выбранном carrier. Такой host-loss drill сегодня **Not Run**.

Решения A1–A6 исходного [Draft плана](../implementation-plan-s08.md#краткая-таблица-архитектурных-решений-a1a6) сохраняются: учебная пауза/clean restore разрешены и проверены; постоянные A2/A4/A6, предел паузы, внешние gates и operator responsibility требуют окончательного утверждения. Оригинальный план не изменён. [Публичный checklist](public-deployment.md), [внешняя интеграция](integration-rehearsal.md).
