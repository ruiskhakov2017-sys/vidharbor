# S03 · Первые проверки T301

**12 ноября 2026 года.** Ветка `feature/s03-queue` от `main` на `a4298d5`. Изолированный проект Compose `vidharbor-s03-t301`, PostgreSQL 16.14, RabbitMQ 4.2 и Pika 1.3.2. В тестовую базу скопирован остановленный том S02, исходный том подключался только для чтения. Для выделения одного сценария в копии остальные ожидающие записи отложены на сутки.

## Доставка задания S02 после остановки брокера

В копии базы сохранено задание `c5c735c7-189f-4a15-b904-d32278a316d5` с `message_id` `428931dd-5c14-45c6-84bd-51fed1b3c982`. После остановки RabbitMQ запущен relay. Запись оставалась неотправленной, запрос PostgreSQL вернул `sent_at IS NULL = true`.

После повторного запуска брокера relay зафиксировал отправку. Проверка реальной очереди `video.jobs` получила сообщение с тем же `message_id` и `job_id`. Свойство `delivery_mode = 2` подтверждает постоянное сообщение. Тест вернул его в очередь без `ack`.

Проверка получила отметку отправки через 26,0 с после начала заключительного опроса. До этого брокер был пересоздан с сохранением тестового тома. После дополнительной остановки и запуска RabbitMQ очередь сохранила это сообщение с тем же ID.

На этой машине штатная проверка здоровья RabbitMQ многократно превышала 8 с и запускала несколько тяжёлых процессов диагностики. Для повторного запуска в тестовом проекте временно отключена только эта Docker healthcheck. Доступность брокера и содержимое очереди проверены фактическим AMQP-соединением. Обычный Compose сохранён со штатной проверкой.

## Маршрут и повтор

- На отдельном тестовом exchange отсутствовала привязка. `mandatory` вернул сообщение `13a506bc-52f0-460a-b0ee-d9b1d0fb2ccf`, а `sent_at` остался пустым. После восстановления маршрута relay получил подтверждение и отметил запись отправленной.
- После фактической публикации сообщения `21d03796-4be9-4179-aa5e-27c5206ed1cd` тест имитировал потерю результата на границе записи в базу. Транзакция откатилась и `sent_at` остался пустым. Повтор доставил вторую копию с тем же `message_id`. Это проверка повторной публикации, вызванной имитацией сбоя после подтверждения брокера.
- Два теста Django `vidharbor.test_relay` прошли за 4,183 с. Они проверяют запись отметки после подтверждения, возврат сообщения и сохранение ID при повторе.

Обработчик и распознавание дублей относятся к T302–T304.

## Дополнительные проверки T301

- При остановленном RabbitMQ через API S02 создана и завершена загрузка WebM. PostgreSQL сохранил задание `60f6a2a3-7a07-4fa8-a04b-7392be6e6c5d` и неотправленный outbox `3ade1837-e6aa-4797-9de5-06465a290f15`. После запуска брокера запись отмечена отправленной через 38,9 с. Реальная рабочая очередь вернула тот же `message_id` и `job_id`. Доставка возвращена в очередь без `ack`.
- Фактический разрыв перед получением publisher confirm воспроизведён локальным TCP-прокси. Прокси пропустил публикацию в RabbitMQ, перехватил подтверждение брокера и закрыл соединение, прежде чем оно дошло до relay. Транзакция оставила `sent_at` пустым для `513f64ab-d27c-43d3-b40a-5bfb6d015238`. После повтора в тестовой очереди обнаружены две копии с тем же `message_id`.

Распознавание повторной доставки обработчиком проверяется в T302–T304. Скрипт эксперимента с прокси находится локально в `test-results/s03/confirm_disconnect.py`.

## Команды

```powershell
docker compose --env-file .env.example build relay
docker compose --env-file .env.example up --no-build --no-deps -d relay
docker compose --env-file .env.example stop rabbitmq
docker compose --env-file .env.example start rabbitmq
docker compose --env-file .env.example run --rm --no-deps -T relay python manage.py test vidharbor.test_relay --noinput -v 2
```

Запуск выполнялся с отдельным `COMPOSE_PROJECT_NAME`, тестовыми секретами и копией тома. Тестовый override отключал healthcheck RabbitMQ, когда его диагностические процессы начали зависать.

## Частичная проверка отправки окончательной ошибки

В relay добавлен маршрут outbox для события video.failed.v1 в exchange video.dead. На PostgreSQL и RabbitMQ проверено отсутствие маршрута в тестовую очередь. Сообщение e3a43f2f-9872-4a79-995e-f6ff622a523a осталось неотправленным в базе. После восстановления привязки relay доставил его с тем же ID. Три теста Django relay прошли за 2,603 с.

Это первоначальная проверка пути через PostgreSQL и relay. Результаты проверки обоих путей — в [протоколе T302–T304](s03-t302-t304.md#t303--два-пути-в-очередь-ошибок).

## Частичная проверка учёта попыток

Добавлены модель Attempt и транзакционные функции учёта. На чистой тестовой PostgreSQL применена миграция 0002. Пять тестов relay и учёта попыток прошли за 5,091 с. В тестах проверены задержки 30 и 120 секунд, окончательная ошибка после трёх попыток, фиксация потерянного worker и отсутствие новой попытки для дублированной успешно завершённой команды.

Проверки с подключённым AMQP-обработчиком — в [протоколе T302–T304](s03-t302-t304.md).
