# T304 · Восстановление после сбоя PostgreSQL и разрыва канала

Проверки выполнены 12 ноября 2026 года на отдельном проекте Docker Compose `vidharbor-s03-full`, с PostgreSQL 16.14, RabbitMQ 4.2.9 и тестовой базой `vidharbor_s03_test`. Сценарии запускали штатный код consumer с тестовой обработкой. В первом сценарии использовался FFmpeg, во втором `flock` удерживал тестовый процесс на общем томе.

## Изменения

- Перед подпиской worker проверяет PostgreSQL командой `SELECT 1`. При ошибке связи закрывает канал без `ack` и проверяет БД каждые 2 секунды. После восстановления сам подписывается снова.
- Сигнал закрытия канала отменяет ожидание файловой блокировки. После получения блокировки поток Pika проверяет, что канал ещё открыт. Перед записью попытки проверка отмены повторяется под блокировкой строки в PostgreSQL.
- Предельное ожидание блокировки — **15 минут** при штатной настройке. По истечении срока канал закрывается без `ack`, сообщение доступно для повторной доставки. Выбранный интервал учитывает лимит повторных доставок quorum-очереди и трёхчасовой лимит FFmpeg. В тесте ожидание сокращено до 12 секунд. [Лимит доставок RabbitMQ](https://www.rabbitmq.com/docs/4.2/quorum-queues#poison-message-handling)

## Длительный сбой PostgreSQL

В `18:00:05.379485 UTC` TCP-прокси закрыл существующие соединения worker с PostgreSQL и перестал пропускать новые. Сбой вызван после записи начала попытки. Контрольное соединение с БД оставалось доступно для наблюдения.

- База для worker недоступна **97,1 с**. В течение **78,1 с** после приостановки подписки семь замеров RabbitMQ показали `consumers=0`, `ready=1`. По журналу сообщение было получено один раз до восстановления.
- В `18:01:42.460141 UTC` связь восстановлена. Тот же worker с PID `22` повторно получил `75d3cfa6-c433-4ccc-ba20-3c94c432e789` с `redelivered=True` и запланировал следующую попытку. Ручной остановки и перезапуска worker в ходе проверки не было.
- В `18:02:32.904077 UTC` задание `88d1a355-d9d5-476d-85ab-e6b9e197b4ff` завершилось. В PostgreSQL остались попытка 1 `RETRY / worker_lost` и попытка 2 `SUCCEEDED`. ID команды второй попытки `904a8e72-c262-4119-bcf7-78bfb060ce1b`.

## Разрывы канала при удерживаемой блокировке

Тестовый процесс захватил файловую блокировку задания `fdd151e2-ffb1-4b3a-b966-88f099fc3cc0` до доставки. Для первых трёх доставок на канале worker запрашивали отсутствующую очередь в пассивном режиме. RabbitMQ закрыл каждый канал с `404 NOT_FOUND` в 18:03:16.161452, 18:03:19.316709 и 18:03:22.693785 UTC и выдал то же сообщение `1e524c6d-d6e8-49c1-a8c1-d8bdd2062d6c` повторно.

| Доставка | Действие | Результат |
|---|---|---|
| 1, 2, 3 | RabbitMQ закрыл канал при удерживаемой блокировке | Ожидания завершились через 0,87 / 0,82 / 0,85 с от начала каждого ожидания. Все три завершились с `cancelled=True` и `acquired=False`. |
| 4 | Блокировку удерживали до истечения тестового таймаута | Ожидание завершилось через 12,00 с. Сообщение вернулось в очередь, счётчик попыток оставался равен 0. |
| 5 | Тестовый процесс освободил блокировку | Только поток пятой доставки вызвал `begin_attempt` и обработчик. В PostgreSQL одна попытка `1 SUCCEEDED`. |

## Повторение на стенде

На ранее созданном изолированном проекте использовались тестовые секреты и существующие образы Compose. Сценарии изменяют очередь тестового проекта.

```powershell
$env:COMPOSE_PROJECT_NAME = 'vidharbor-s03-full'
$env:VIDHARBOR_DB_NAME = 'vidharbor_s03_test'
$env:VIDHARBOR_SECRETS_DIR = (Join-Path $PWD 'test-results/s02/secrets')
$override = Join-Path $PWD 'test-results/s03/full-test.yaml'
$api = Join-Path $PWD 'api'
$checks = Join-Path $PWD 'test-results/s03'
$worker = Join-Path $PWD 'scripts/s03_test_worker.py'
docker compose --env-file .env.example -f compose.yaml -f $override start db rabbitmq
docker compose --env-file .env.example -f compose.yaml -f $override run --rm --no-deps -T -e PYTHONPATH=/app --volume "$($api):/app:ro" --volume "$($checks):/checks:ro" --volume "$($worker):/s03_test_worker.py:ro" upload sh -ec 'python -u /checks/t304_db_pause_check.py; python -u /checks/t304_lock_channel_check.py'
docker compose --env-file .env.example -f compose.yaml -f $override run --rm --no-deps -T --volume "$($api):/app:ro" upload python manage.py test vidharbor --noinput -v 2
```

Оба сценария прошли. Все 9 тестов Django прошли за 29,419 с, включая отдельную проверку отмены доставки перед записью попытки и планированием повтора.

После проверок контейнеры тестового Compose остановлены, тома сохранены.
