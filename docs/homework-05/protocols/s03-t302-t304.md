# S03 · Попытки, очередь ошибок и восстановление

Проверки выполнены 12 ноября 2026 года в отдельных проектах Docker Compose `vidharbor-s03-full` и `vidharbor-s03-policycheck`. Использованы PostgreSQL 16.14, RabbitMQ 4.2.9 из закреплённого образа и тестовые секреты. Миграции `0001` и `0002` применены к пустой базе. На копии базы S02 миграция `0002` сохранила исходные задание и outbox. [Протокол T301](s03-t301.md).

Обработчик запускался через `scripts/s03_test_worker.py` с `VIDHARBOR_S03_TEST_ONLY=1` и базой `vidharbor_s03_test`. Сценарии вызывали рабочий код relay и consumer с настоящими PostgreSQL и RabbitMQ. Для испытаний с живым FFmpeg использован общий том Compose. В сценарии таймаута подтверждения политика брокера в тестовом проекте выставлена на 60 секунд. В обычном Compose RabbitMQ применяет политику с таймаутом 4 часа. Штатный запуск включает relay, тестовый worker запускается отдельно.

## T302 · Ручной ack и попытки

- Задание `ed01d757-a1f3-429e-958d-49dc314fd729` получило одну попытку `SUCCEEDED`. После повторной доставки счётчик остался равен 1. Видео в кабинете осталось в статусе ожидания обработки. В БД фиксировался результат тестового задания.
- При временной ошибке проверены три попытки с паузами 30 и 120 секунд. До окончательного исхода прошло 151,4 секунды. Записи попыток — `1 RETRY`, `2 RETRY`, `3 FAILED`. Для задания с неисправимым форматом тестовый обработчик зафиксировал `FAILED` после первой попытки.
- Перезапуск между попытками проверен при сбоях worker и PostgreSQL. Счётчик остался в базе и продолжился со следующего номера.

## T303 · Два пути в очередь ошибок

В RabbitMQ удалили привязки маршрутов к `video.dlq`. После восстановления получили оба сообщения с исходными ID.

| Путь | ID сообщения | Наблюдение |
|---|---|---|
| Окончательная ошибка задания | `22b588ed-163a-4443-b6b3-f5792b081cc7` | Outbox остался в PostgreSQL без `sent_at`. После восстановления привязки relay отправил событие с подтверждением. |
| Сообщение с неразбираемым телом | `ec22de16-fbe6-4940-bb88-1871016a97d9` | Worker отклонил сообщение без возврата в рабочую очередь. RabbitMQ записал `Cannot forward any dead-letter messages from source quorum queue`, сохранил сообщение и переслал его в DLQ после восстановления привязки. |

Quorum-очередь `video.jobs` получила политику `at-least-once` с `reject-publish`. Исправное задание `7cb769c5-5a0d-4780-87dd-7aec4f689d71` после неисправного дошло до `SUCCEEDED`.

Временный оператор RabbitMQ смог прочитать только очередь ошибок. Чтение рабочей очереди вернуло 403. В сообщении f7ea8eaa-75e7-428c-8fdb-4dafc397452c заголовок x-death содержал причину rejected. Роль PostgreSQL с SELECT на истории попыток прочитала RETRY / worker_lost и SUCCEEDED, право UPDATE отсутствовало.

## T304 · Повторная выдача и блокировка

| Сбой | Фактический результат |
|---|---|
| `SIGKILL` worker перед записью результата | Задание `d8d6fc1f-251d-4b0c-af33-b14c259a8ff5`. Старый FFmpeg продолжал писать, файл вырос с 0 до 142 504 байт. Повторный worker ждал блокировку и счётчик оставался равен 1. После выхода FFmpeg попытка 1 получила `RETRY / worker_lost`, попытка 2 — `SUCCEEDED`. |
| Пропущенный heartbeat | После `SIGSTOP` worker RabbitMQ в 16:37:00.263032 UTC закрыл соединение с причиной `missed heartbeats from client, timeout: 6s`. Повторно выдано `5663599b-4a7c-41a1-bb76-8076cac2b6f1` с `redelivered=True`. До снятия блокировки старый FFmpeg записал 711 392 байта, число попыток оставалось равным 1. Повтор `240cbe5c-52de-4b41-8a93-c0f3d8fda6a8` завершил задание. |
| Таймаут ack при действующем соединении | RabbitMQ в 16:43:06.410321 UTC закрыл канал с `precondition_failed` из-за просроченного подтверждения `60000 ms`. Событие наблюдалось через 119,8 секунды. Повторно выдано `e2633d7b-a53b-4152-a4d5-d19a0d06dda1`. Пока старый FFmpeg писал, файл вырос до 3 475 180 байт, счётчик оставался равен 1. Результат зафиксирован один раз, затем контрольное чтение подтвердило пустую рабочую очередь. |
| Обрыв соединения с PostgreSQL во время FFmpeg | TCP-прокси закрыл соединения worker с базой. При записи результата worker зафиксировал ошибку, канал закрылся без `ack`. RabbitMQ повторно выдал `c0126fcb-ff62-4dcf-a32b-e1c286045c8d`. После восстановления связи задание `02e6359f-c091-40f9-8bee-85e096ac088f` получило `RETRY` и `SUCCEEDED`. |
| SIGKILL после коммита до ack | Для задания 04d8b9c8-06fa-4269-aa7a-bd6de2a397a6 результат уже был в PostgreSQL, а отправку ack приостановили перед постановкой обратного вызова Pika. После SIGKILL RabbitMQ выдал тот же message_id ad614ed6-149a-4817-94e2-e0fd80e2114b. Новый worker подтвердил его без вызова обработчика. Время окончания единственной попытки (ID 18) сохранилось. |

Перезапуск RabbitMQ и потеря подтверждения публикации проверены с повторной выдачей того же ID. [Протокол T301](s03-t301.md).

Дополнительные проверки паузы подписки при длительном сбое PostgreSQL и отмены ожидания блокировки при потере канала приведены в [регрессии T304](t304-recovery-regression.md).

## Регрессия S01 и S02

- Образы собраны, миграции на новой базе применены. Первоначальный запуск задержали трёхсекундные проверки здоровья API и upload. Контрольный запрос из контейнера вернул 200. После перехода healthcheck на BusyBox wget и увеличения таймаута Compose запустил все сервисы.
- На Chrome 157.0.8103.51 проверены два автора, прогресс от 0 до 100, отказ в доступе к чужой загрузке и CSRF, обрыв и повторная загрузка, повтор завершения после потери ответа. SHA-256 оригиналов совпали, по одному заданию и одной записи outbox на файл. Relay на время браузерной проверки остановлен, чтобы существующий сценарий S02 мог проверить ожидающую запись outbox.
- После запуска relay оба задания оставались QUEUED, у обеих записей outbox заполнен sent_at. В quorum-очереди video.jobs находились 2 сообщения, число потребителей — 0.
- На PostgreSQL прошли все 8 тестов Django за 32,619 с, включая очистку загрузок и восстановление после сбоя между перемещением файла и коммитом. Проверка миграций не нашла незаписанных изменений.

- При остановке RabbitMQ и PostgreSQL по отдельности live оставался 200, ready возвращал 503 с указанием недоступной зависимости и снова 200 после запуска. Встроенный вызов Chrome с --dump-dom в smoke S01 достиг локального таймаута 30 секунд. Проверки страницы и загрузки прошли отдельным сценарием S02 через Playwright и Chrome, проверки HTTP — через test-results/s03/health_regression.py.

## Команды

```powershell
docker compose --env-file .env.example up --build -d --wait --wait-timeout 300
docker compose --env-file .env.example ps -a
docker compose --env-file .env.example logs migrate
docker compose --env-file .env.example exec -T rabbitmq rabbitmqctl list_policies
python scripts/smoke_s02.py test-results/s02/author-a.mp4 test-results/s02/author-b.webm
docker compose --env-file .env.example stop
```

Для тестов с отказами использован отдельный проект `vidharbor-s03-full` с базой `vidharbor_s03_test` и сценариями в локальном каталоге `test-results/s03`. Каждый сценарий запускался через `docker compose run --rm --no-deps -T upload` с подключённым тестовым файлом. Для лабораторных тестов с отказами использован временный Compose override с отключённой проверкой здоровья брокера. Обычная конфигурация проверена отдельно без этого override.
